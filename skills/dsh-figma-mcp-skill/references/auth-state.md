# 写操作前的 token 状态判断

本 reference 与 SKILL.md 第 1 节第 2 步（确认 token 状态）以及第 2 节"修改 Figma 上的现有设计"
任务结合使用：在发起任何写操作前，依据此处规则判断 token 状态。

`mcp__figma__*` 工具背后是一个 Bearer token，由 DSH 客户端管理（落地位置取决于宿主与 profile 布局，
本 skill 不假设具体路径）。本 skill 不直接调用 OAuth 后端 API（`/api/figma/login/start` 等属于宿主端职责）；
仅承担两项工作——协助 Agent 判断 token 状态，以及在需要时引导用户前往设置卡片重新连接。

## 卡片状态与 Agent 操作建议

用户在 DSH 的 `设置 → DSH Figma MCP` 卡片上可观察到以下状态：

| 卡片状态 | 含义 | 写操作前 Agent 的建议动作 |
|---|---|---|
| 未连接 | 尚未获得 token | 暂停写操作，提示用户点击「连接 Figma」启动 OAuth |
| 已连接（绿） | token 有效 | 可直接进行写操作 |
| 即将过期（黄） | 剩余有效时长不足 24 小时 | 可进行写操作，建议提醒用户点击「刷新授权」续期 |
| 已过期（红） | token 失效 | 暂停写操作，提示用户点击「重新授权」（将打开浏览器重走 OAuth 流程） |
| 加载中 | 状态尚未返回 | 稍候片刻，先告知用户"等待连接状态确认"，无需立即判断 |

## 如何确认当前状态

不宜通过"先尝试一次写操作、再观察报错"的方式反推状态——这一过程成本过高且可能造成误操作。

可行的方式包括：

- 让用户自行查看卡片（最为稳妥）；
- 由 Agent 调用一次**只读**的轻量操作（如 `mcp__figma__whoami`，或 `get_metadata` 配合已知存在的 fileKey），
  在失败时引导用户重新连接。该只读探测无需对每次写操作都执行——当卡片状态清晰时可直接采用。

## OAuth 引导方法（供 Agent 参考）

- 未连接 → "Figma 尚未连接，请先前往「设置 → DSH Figma MCP」点击「连接 Figma」，完成授权后即可继续。"
- 已过期 → "Figma token 已过期，请前往「设置 → DSH Figma MCP」点击「重新授权」（会弹出浏览器），完成后我再继续。"
- 即将过期 → "token 剩余有效时长不足 24 小时，是否先前往「设置 → DSH Figma MCP」点击「刷新授权」续期？"

## 注意事项

- OAuth 只能由用户在设置卡片中手动发起、在浏览器中完成；Agent 无法代为登录，也不应尝试调用 `/api/figma/login/start` 等宿主端 HTTP 路由；
- 完整 token 不应写入对话历史、commit、输出文件或 README。Agent 自身调用 MCP 时，应通过 harness 注入的 `mcp__figma__*` 工具进行，无需查看 token 明文；
- token 失效后，不应通过反复重试绕过——失败时宜暂停操作并引导用户刷新或重新授权。
